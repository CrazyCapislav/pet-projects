## Задача

Чтение нескольких десятков блогов вручную не масштабируется: приходится обходить сайты по одному и держать в голове, что уже читал. RSS решает половину проблемы — даёт машиночитаемый список публикаций, — но остаётся вторая: кто-то должен регулярно опрашивать источники, складывать результат в одно место и не показывать одну и ту же статью дважды.

feedhub — серверная часть такого агрегатора. Наружу торчит REST API и лёгкий веб-интерфейс поверх него.

Задача выбрана намеренно: в ней естественно возникают четыре вещи, которых нет в типовом CRUD, — **конкурентность**, **ненадёжный внешний мир**, **растущий объём данных** и **гарантии целостности**.

## Возможности

- **Подписки** — добавление по URL с немедленной первой загрузкой, тематические теги, ручное включение отключившихся лент.
- **Фоновый обход** по расписанию: все ленты опрашиваются параллельно с ограничением конкурентности, поддерживается условный GET (`ETag` / `If-Modified-Since`).
- **Отказоустойчивость** — таймауты, счётчик подряд идущих ошибок, автоматический перевод «мёртвых» лент в `DISABLED`, пропуск битых записей вместо падения всей ленты.
- **Дедупликация** на двух уровнях: по `guid` внутри ленты и по канонической ссылке между лентами (перекрывающиеся общий и тематический фиды сайта).
- **Лента статей** — фильтры по подписке, тегу и статусу прочтения, полнотекстовый поиск PostgreSQL, постраничная навигация.
- **Форматы** — RSS 2.0, RDF и Atom 1.0; парсер написан на JDK DOM с защитой от XXE.

## Быстрый старт

Нужны JDK 21 и Docker.

```bash
git clone https://github.com/CrazyCapislav/feedhub && cd feedhub
./gradlew bootRun
```

Spring Boot сам поднимет PostgreSQL из `compose.yaml`, Flyway накатит схему и добавит несколько живых лент. Первый обход произойдёт через ~15 секунд после старта.

| Что | Адрес |
|---|---|
| Веб-интерфейс | http://localhost:8080 |
| Swagger UI | http://localhost:8080/swagger-ui.html |
| Health-check | http://localhost:8080/actuator/health |
| Метрики Prometheus | http://localhost:8080/actuator/prometheus |

Полностью в контейнерах:

```bash
docker build -t feedhub .
docker compose --profile full up -d
```

Тесты (нужен Docker — интеграционные поднимают PostgreSQL через Testcontainers):

```bash
./gradlew test
```

## Архитектура

```
src/main/kotlin/dev/rahim/feedhub/
├── config/       типобезопасная конфигурация, WebClient, OpenAPI
├── domain/       сущности JPA и доменное поведение
├── repository/   Spring Data JPA, спецификации, массовые операции
├── fetch/        ядро: загрузка, разбор, конкурентный обход, запись
├── service/      бизнес-логика, доменные ошибки
└── web/          контроллеры, DTO, обработчик исключений
```

Слои разделены строго: `web` не знает про JPA, `service` не знает про HTTP, `fetch` не знает про формат ответа. Наружу отдаются DTO, а не сущности — иначе публичный контракт оказался бы привязан к схеме БД.

## Цикл обновления

Самая содержательная часть проекта.

```
FeedRefreshScheduler         @Scheduled → runBlocking (граница с фреймворком)
        │
        ▼
FeedRefreshService           coroutineScope: fan-out по всем активным лентам
        │                    async { } на каждую + Semaphore(8) на HTTP
        ▼
FeedFetcher                  suspend, условный GET, таймаут   ← неблокирующе
        │
        ▼
RssParser                    RSS 2.0 / Atom → ParsedFeed       ← CPU
        │
        ▼
ArticleIngestService         withContext(Dispatchers.IO)       ← блокирующе
                             @Transactional, дедупликация, batch insert
```

Три решения, которые здесь важны:

**Ограничение конкурентности.** Двадцать лент по ~300 мс — это шесть секунд последовательно и меньше секунды параллельно. Но двадцать одновременных запросов исчерпали бы пул соединений и привели бы к блокировкам на стороне чужих сайтов, поэтому число одновременных загрузок ограничено семафором.

**Граница блокирующего и неблокирующего кода.** JDBC блокирует поток, а спринговая транзакция привязана к нему через `ThreadLocal`. Поэтому методы записи — обычные `@Transactional`-функции, а не `suspend`, и вызываются они через явный `withContext(Dispatchers.IO)`. Обратный подход приводит к транзакциям, «теряющимся» при возобновлении корутины в другом потоке.

**Типы вместо исключений для ожидаемых исходов.** `FetchOutcome` — sealed-иерархия из трёх вариантов: тело, `304 Not Modified`, ошибка. Компилятор требует обработать каждый, поэтому добавление нового исхода не может быть тихо пропущено.

## Модель данных

```
feeds ──1:N──> articles          подписка и её статьи
  │
  └──M:N──> tags                 тематические метки
```

| Таблица | Назначение |
|---|---|
| `feeds` | URL, заголовок, статус, валидаторы условного GET, счётчик ошибок |
| `articles` | заголовок, ссылка, каноническая ссылка, дата, флаг прочтения |
| `tags`, `feed_tags` | тематические метки подписок |

Индексы подобраны под реальные запросы: составной `(feed_id, published_at desc)` для ленты одной подписки, частичный `where is_read = false` для фильтра непрочитанного, GIN по выражению — для полнотекстового поиска.

## API

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/feeds` | подписки со счётчиками статей |
| `POST` | `/api/feeds` | добавить подписку и сразу загрузить |
| `DELETE` | `/api/feeds/{id}` | удалить подписку вместе со статьями |
| `PUT` | `/api/feeds/{id}/tags` | заменить набор тегов |
| `POST` | `/api/feeds/{id}/read-all` | отметить прочитанной всю ленту |
| `POST` | `/api/feeds/{id}/enable` | вернуть в строй отключённую ленту |
| `POST` | `/api/feeds/{id}/refresh` | обновить одну ленту немедленно |
| `POST` | `/api/feeds/refresh` | обновить все ленты |
| `GET` | `/api/articles` | лента статей с фильтрами и пагинацией |
| `POST` | `/api/articles/{id}/read` | пометить статью прочитанной |
| `DELETE` | `/api/articles/{id}/read` | снять отметку |
| `POST` | `/api/articles/read-all` | отметить прочитанным всё |
| `GET` | `/api/tags` | теги с числом подписок |

Параметры `GET /api/articles`: `feedId`, `tag`, `unreadOnly`, `search`, `page`, `size` (максимум 100).

Ошибки — RFC 7807 Problem Details:

```json
{ "type": "https://feedhub.dev/errors/404", "title": "Not Found",
  "status": 404, "detail": "Не найдено: Лента с id=42" }
```

Полный контракт: `/swagger-ui.html` при запущенном приложении.

## Технические решения

Наиболее интересные компромиссы, принятые в проекте.

**Полнотекстовый поиск вместо `LIKE '%…%'`.** Подстрочный поиск давал ложные срабатывания — запрос «ai» находил «domain» и «available» — и не мог использовать индекс из-за ведущего процента. Заменён на `tsvector` + GIN-индекс по выражению; поиск работает по словам и с учётом словоформ. Конфигурация `english` выбрана осознанно: для смешанных по языку лент альтернативой был бы отдельный вектор на каждый язык.

**Дедупликация на двух уровнях.** Уникальность `(feed_id, guid)` в БД — единственная надёжная защита от дублей внутри ленты: две параллельные загрузки одного источника проходят проверку в коде одновременно. Между лентами сравниваются канонические ссылки, очищенные от `utm_*` и прочих меток, — иначе общий и тематический фиды одного сайта дают один и тот же материал дважды.

**`ddl-auto: validate` и Flyway как единственный источник правды.** `update` не удаляет и не переименовывает колонки, поэтому схема на проде незаметно расходится с ожидаемой. `validate` не даёт приложению стартовать при расхождении.

**`open-in-view: false` и явная загрузка связей.** Открытая на весь запрос сессия Hibernate прячет N+1 внутри сериализации JSON, где его не видно ни в одном логе. Связь `Article → Feed` объявлена ленивой, а нужные выборки помечены `@EntityGraph` — один JOIN вместо запроса на каждую строку.

**Массовые операции без загрузки сущностей.** «Отметить всё прочитанным» — один `UPDATE` через `@Modifying`, а не выгрузка сотен объектов в память. Персистентный контекст очищается после выполнения, иначе Hibernate продолжил бы отдавать устаревшие объекты из кэша первого уровня.

**Защита от XXE.** Разбирается XML, пришедший из интернета, поэтому внешние сущности и DOCTYPE отключены явно: без этого чужая лента может заставить сервис прочитать локальный файл или обратиться во внутреннюю сеть. Поведение закреплено регрессионным тестом.

**`URI.create()` вместо строки в `WebClient`.** Строка трактуется как URI-шаблон, и ссылка с фигурными скобками ломает запрос.

**Условный GET.** Сохранённые `ETag` и `Last-Modified` возвращаются серверу при следующем обходе; на неизменившихся лентах ответ `304` экономит трафик и снижает нагрузку на чужие сайты.

## Тестирование и CI

**35 тестов** в трёх слоях:

- **юнит-тесты парсера** (9) — форматы дат, битая разметка, чистка HTML, регрессия на XXE; без Spring и БД, выполняются за миллисекунды;
- **юнит-тесты канонизации ссылок** (6) — правила отбрасывания трекинговых параметров;
- **интеграционные тесты API** (19) — настоящий PostgreSQL в Docker через Testcontainers, реальные миграции Flyway, HTTP-слой через MockMvc; проверяют фильтры, полнотекстовый поиск, массовые операции, работу с тегами и формат ошибок;
- **smoke-тест контекста** (1).

**GitHub Actions** на каждый push и pull request: сборка, прогон всех тестов, сборка Docker-образа. Отчёт о тестах публикуется артефактом.

## Наблюдаемость

- `/actuator/health` — состояние приложения и доступность БД, с разделением на `liveness` и `readiness` для оркестратора;
- `/actuator/prometheus` — метрики Micrometer, включая собственные: `feedhub.refresh.cycle` (длительность обхода), `feedhub.refresh.feeds{outcome}` (счётчик исходов по лентам), `feedhub.articles.ingested`;
- структурированные логи с итогом каждого цикла обновления.

В профиле `prod` детали health-check скрыты: они раскрывают версию СУБД, пути на диске и объём свободного места.

## Конфигурация

Настройки фонового обхода вынесены в типобезопасный `@ConfigurationProperties`:

```yaml
feedhub:
  refresh:
    enabled: true                  # выключатель планировщика
    interval: PT10M                # пауза между циклами
    timeout: PT15S                 # таймаут на одну ленту
    max-concurrent: 8              # одновременных загрузок
    max-failures-before-disable: 5 # ошибок подряд до отключения ленты
    cross-feed-deduplication: true
```

Профиль `prod` берёт параметры БД из переменных окружения `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`.

## Что можно развивать дальше

- **Адаптивное расписание** — часто обновляемые ленты опрашивать чаще, «спящие» реже, с экспоненциальным backoff после ошибок.
- **Кэш и rate limiting** — Redis для ленты статей и ограничение частоты обращений к одному хосту.
- **Пользователи** — Spring Security и привязка подписок к аккаунту.
- **OPML** — импорт и экспорт списка подписок для переноса из других читалок.
- **Ранжирование по релевантности** в полнотекстовом поиске вместо сортировки только по дате.

Проект намеренно не разбит на микросервисы и не использует брокер сообщений: на текущем объёме это добавило бы инфраструктурную сложность, не решая ни одной реальной проблемы.
